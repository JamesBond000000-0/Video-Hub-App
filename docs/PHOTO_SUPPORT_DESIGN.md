# 写真対応 設計書 (PHOTO_SUPPORT_DESIGN)

Video Hub App 3 フォークに、動画に加えて写真 (静止画ファイル) をオプションで
取り込めるようにする機能の設計と見積もり。対象は統合ブランチ
`integration/tauri-face-recognition` (Electron / Tauri 両ランタイム、
ハブ形式 .vha2 は共有)。

## 1. 現状 (実コードで確認済み)

- 取り込み対象は動画 32 拡張子のみ。リストは2箇所に重複して存在する:
  - Electron: `node/main-filenames.ts` の `acceptableFiles`
  - Tauri: `src-tauri/src/media.rs` の `ACCEPTABLE_EXTENSIONS`
- データ形式 `FinalObject` (`interfaces/final-object.interface.ts`):
  `images: ImageElement[]` が全要素を持つ。`ImageElement` は動画前提の
  フィールドを含む:
  - `duration` (秒)、`bitrate` (= fileSize / duration で算出)、`fps`
  - `screens` (スクリーンショット数)、`defaultScreen`
  - `width` / `height`、`hash` (ファイル内容サンプル方式、形式非依存)
  - 任意フィールドの前例がある (`persons`、`tags`、`notes` 等)。
    `FinalObject.faceSettings?` も「任意 + 開いた時に既定値を補完」で
    追加されており、形式の版上げなしで設定を足せる前例になっている。
- メタデータ取得は両ランタイムとも ffprobe。Tauri 側は
  `media.rs::extract_metadata` が duration から
  `hub::compute_number_of_screenshots` で screens を決める
  (fixed モードでは duration に関係なく n 枚になる点に注意)。
- サムネイルは `<hub>/thumbnails/<hash>.jpg` に集約され、filmstrip /
  clips (ホバープレビュー用の動画断片画像) も別途生成される。
  ギャラリー表示は thumbnail / filmstrip / full / clip / details の
  各ビューコンポーネントが担う。
- ファイルを開く主経路は OS の既定アプリでの外部起動 (動画プレイヤー)。
  これは写真でもそのまま画像ビューアが開くため流用できる。
- 顔認識スキャンは `sampleTimes(duration, interval, maxFrames)` で
  時刻を決め ffmpeg でフレームを抜く。duration = 0 では時刻が負になり
  そのままでは動かない (後述 P5)。

## 2. 設計判断

### P1: 写真要素の表現 — `ImageElement` に任意フィールドを追加

- `kind?: 'photo'` を追加する。不在 = 動画として扱い、既存ハブは無変更で
  開ける (faceSettings / persons と同じ後方互換パターン)。
- 拡張子から都度判定する案は採らない。リネームや将来の形式追加で
  表示・顔スキャン側の分岐が散らばるため、取り込み時に確定させる。
- 写真要素の動画前提フィールドは以下で固定する:
  `duration = 0`、`fps = 0`、`bitrate = 0` (0 除算回避)、
  `screens = 1`、`width` / `height` は実寸。

### P2: 設定 — ハブ単位のトグル、既定 OFF (2026-11-01 決定)

- `FinalObject.photoSettings?: { enabled: boolean }` を追加し、
  faceSettings と同じく開いた時に既定値 (enabled: false) を補完する。
- トグルは「取り込み (スキャン)」だけを制御する。OFF に戻しても
  取り込み済みの写真要素はハブに残る (削除は通常の要素削除で行う)。
- 設定 UI は既存の設定画面に顔認識と並べて置く。

### P3: 対応形式 — ffmpeg / ffprobe が扱えるものに限る (2026-11-01 決定)

- 走査の候補拡張子は画像形式を広めに取る (jpg / jpeg / png / webp /
  bmp / gif / tiff / avif / heic / heif 等) が、取り込み可否は
  ffprobe が実際に寸法を返したものに限る (probe 検証方式)。
- 本アプリの ffmpeg / ffprobe は同梱でなく PATH 上のものを使うため、
  実際に扱える形式はユーザーの ffmpeg ビルド次第になる。HEIC 等も
  ビルドが対応していれば自動的に対象になる。
- GIF のアニメーションは静止画 (先頭フレーム) として扱う。

### P4: サムネイル — 写真自身を縮小して使う

- 写真の「スクリーンショット」は画像そのものをスクリーンショット
  高さ設定 (144〜504) に合わせて縮小し `thumbnails/<hash>.jpg` に置く。
  ギャラリー側の参照方法は動画と同一になり、表示側の変更が最小化する。
- filmstrip / clips は生成しない (ビュー側は kind で分岐)。
- EXIF の回転情報 (Orientation) は縮小時に反映されることを検証項目に
  入れる。ffmpeg の自動回転が効く見込みだが、実機のスマホ写真で確認する。

### P6: 保管場所 — `images[]` に同居する (2026-11-01 決定)

- 写真要素は別の配列 (例: `photos[]`) に分けず、`images[]` に
  `kind: 'photo'` で同居させる。別配列案は検討の結果、不採用。
- 理由: レンダラの合流点は `home.component.ts` の1箇所だが、ハブの
  `images` は両ランタイムのバックエンド (開く/再スキャン/保存/
  顔の persons 書き戻し) が広く前提にしており、別配列にすると
  全箇所が2配列の合流/分離か二重処理になる (実測ベースで +2〜3日、
  以後の要素に触る機能すべてに分離の意識が残る)。
- 本家互換は「形式は読めるが、本家での再保存では写真要素が劣化し
  得る」を許容する (persons / faceSettings と同じ方針)。別配列でも
  `photoSettings` は本家には未知であり、互換が完全にはならない。

### P5: 顔認識 — 写真は「1フレーム」として処理

- スキャン側は写真要素を単一フレームとして扱う分岐を追加する
  (t = 0 の1枚のみ。`sampleTimes` の duration = 0 問題を回避)。
  画像ファイルをそのまま検出器に渡す経路でもよい (実装時に選択)。
- `persons` キャッシュや人物 UI は要素単位で既に汎用なので流用できる。
- `faceSettings.autoScanNew` の自動スキャン対象にも写真が入る。

## 3. フェーズ計画と見積もり

作業量は本フォークでの実装 + VM 上の検証まで。実機確認はユーザー側。

**実施順序は Tauri 先行 (2026-11-01 決定)**: バックエンド側の作業は
まず Tauri (Rust) のみで行い、Electron (node) 側は後続で追随する。
レンダラ (Angular) は両ランタイム共通のため一本化する。
Tauri 先行分の合計は 3〜5 日相当、Electron 追随は +1〜2 日。

| Phase | 内容 | 量 | 検証 |
|---|---|---|---|
| 0 | データ形式と設定: `kind` / `photoSettings` の型・既定値補完・設定 UI トグル (両ランタイムで FinalObject を読む側の追随) | 小 (0.5日) | 既存ハブが無変更で開けること、tsc / cargo test |
| 1 | 取り込み: 両ランタイムの拡張子リストに写真分岐を追加 (トグル連動)、ffprobe メタデータ (duration=0 の扱い、寸法、hash は既存方式) | 中 (1〜1.5日) | 写真フォルダでハブ作成、要素が期待通り入ること |
| 2 | サムネイルと表示: 写真の縮小生成 (P4)、screens=1 の扱い、ギャラリー各ビューの分岐 (時間表示を出さない、filmstrip/clips を要求しない) | 中 (1〜1.5日) | 各ビューで写真が崩れず表示されること |
| 3 | 閲覧: 内蔵ビューアを実装する (2026-11-01 決定)。最小構成のライトボックス (クリックで拡大表示、前後送り、Esc・背景クリックで閉じる、クリックで等倍⇔フィット切替)。原寸の届け方はプレビューコピー方式: 取り込み時に長辺 1920px 程度のプレビューをハブ内に生成し、動画サムネイルと同じ経路で出す (asset スコープは広げない)。EXIF 回転はプレビュー生成時に焼き込む。外部起動も従来通り併用可 | +1〜2日 | プレビュー表示・前後送り・回転の実証 |
| 4 | 顔認識: スキャンの写真分岐 (P5)、自動スキャン、人物表示の確認 | 小〜中 (0.5〜1日) | 写真から人物が検出・分類されること (ゴールデン比較は不要、動作確認中心) |
| 5 | 仕上げ: EXIF 回転の実証、長さ・解像度フィルタやソートでの写真の扱いの整合、文言 (「動画」表記) の調整 | 中 (1日) | フィルタ/ソートの実測、スマホ写真での表示確認 |

**合計の目安: Tauri 先行 + ビューア込みで 4〜7 日相当**、
Electron 追随は +1〜2 日。
見積もりの不確実性は主に Phase 2 / 5 のレンダラ側の長尾
(右クリックメニュー、再生回数やプレイリスト等の動画前提 UI の扱い) にある。

## 4. リスク・未決事項

- **.vha2 の版**: 任意フィールド追加のみで `version` は上げない方針
  (faceSettings の前例)。本家で開いた場合の内訳: 形式は読め、要素と
  サムネイル (`<hash>.jpg` の約束) は残る見込み。一方で本家は写真を
  duration=0 の動画として扱い、filmstrip やスクリーンショット再生成で
  劣化し得る。本家の再スキャン系処理がメタデータの取れない要素を
  落とすかどうかは未検証 (Phase 5 の確認項目)。方針は P6 の通り
  「読めるが劣化し得る」を許容する。
- **EXIF 回転**: 縮小パイプラインで Orientation が反映されないと
  スマホ写真が横向きに表示される。Phase 2 で実証する。
- **大容量写真**: 1ファイル数十 MB の RAW 級は対象外 (P3 の形式で除外済み)。
  JPEG でも大量 (数万枚) のハブでのスキャン時間は未計測。
- **動画前提 UI の扱い**: 再生回数 `timesPlayed`、プレイリスト、
  「スクリーンショット再生成」等のメニューを写真でどう見せるかは
  Phase 2 / 5 で個別に決める (基本は無効化または非表示)。
- **対象ランタイムの順序**: Tauri 先行で確定 (P3 のフェーズ計画参照)。
  Electron で開いたハブに写真要素が混ざる期間が生じるが、P6 の互換
  方針の範囲として許容する。

## 5. 決定事項まとめ (2026-11-01 確定)

- 保管場所: `images[]` に `kind: 'photo'` で同居 (別配列は不採用) — P6
- 設定: ハブ単位 `photoSettings`、既定 OFF、取り込みのみ制御 — P2
- 対応形式: ffmpeg / ffprobe が扱えるもの (広めの候補拡張子 + probe 検証) — P3
- サムネイル: 写真自身の縮小を `thumbnails/<hash>.jpg` に配置 — P4
- 顔認識: 写真は1フレームとして処理 — P5
- 閲覧: 内蔵ビューア (最小構成ライトボックス) + プレビューコピー方式
  (長辺 1920px、EXIF 回転を焼き込み、asset スコープは広げない) — Phase 3
- 実施順序: Tauri 先行、Electron は後続で追随
- 見積もり: Tauri 先行 + ビューア込み 4〜7 日相当、Electron 追随 +1〜2 日
