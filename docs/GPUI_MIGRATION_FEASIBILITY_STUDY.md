# GPUI への移植可能性の検討（Feasibility Study）

## 1. エグゼクティブサマリー

### 背景と目的
本プロジェクト（Video Hub App 3 フォーク）は、大量のローカル動画・静止画を閲覧・検索・管理するデスクトップアプリケーションであり、顔認識による人物分類機能を統合している。
現在、UI ランタイムとして **Angular (Chromium / WebView)** を採用し、デスクトップシェルとして **Electron**（安定版）および **Tauri 2**（移行中ブランチ）の 2 系統が併存している。

本検討では、Zed エディタ等で採用されている Rust 製の GPU 高速描画 UI フレームワーク **GPUI**（https://github.com/zed-industries/zed/tree/main/crates/gpui）へのフルネイティブ移植の技術的実現可能性、メリット・デメリット、開発工数、およびリスクを評価・分析する。

### 結論（Verdict）
- **短期的な直接移行は「非推奨（リスク過大）」**。
- **長期的・段階的なアプローチとしては「極めて魅力的だが、UI/エコシステムの成熟待ちが必要」**。
- **現時点の推奨戦略**:
  1. 現在進行中の **Tauri 2 へのバックエンド統合（Rust 化）を完遂**する。
  2. メディアスキャン、メタデータ抽出、顔認識・推論、ハブ永続化ロジックなどの Rust コアクレートを WebView 非依存の独立クレートとして設計・分離する。
  3. GPUI のエコシステム（特にマルチプラットフォーム対応、アクセシビリティ、CJK 入力（IME）、動画プレビュー等のウィジェット群）の成熟度を注視しつつ、独立した PoC（プロトタイプ）で段階的検証を行う。

## 2. 現在のアーキテクチャと資産状況

### 2.1 全体構成
```
[ レンダラ層 (UI) ]
  - Angular 20 + TypeScript (~13,600 行)
  - HTML (~5,400 行) + SCSS (~4,300 行)
  - ngx-virtual-scroller (数万件のサムネイル仮想スクロール)
  - i18n (多言語対応)
  - 複雑なフィルタ/ソートパイプ (40+ pipes/services)

      ↕ (IPC: sendToMain / receiveFromMain)

[ バックエンド層 (デスクトップ / メディアエンジン) ]
  - Electron main (Node.js) & Tauri 2 (Rust ~6,550 行)
  - FFmpeg / FFprobe によるメディア抽出・ハッシュ計算
  - ONNX Runtime (ort) による SCRFD 顔検出 & ArcFace/LVFace 特徴量抽出
  - ハブ永続化 (JSON .vha2 + Float32LE バイナリ embeddings.bin)
```

### 2.2 主要な機能要件
1. **仮想スクロールと大容量サムネイル表示**:
   - 1ハブあたり数千〜数万件の動画サムネイル・フィルムストリップ・クリップの高速描画。
2. **動画/アニメーションプレビュー**:
   - サムネイルホバー時のフィルムストリップ切り替え、クリップ（MP4）プレビュー再生、内蔵写真ビューア。
3. **リッチな操作系**:
   - 複雑な検索フィルタ（タグ、解像度、星評価、人物、ワードクラウド、正規表現、類似度）。
   - モーダルダイアログ、トレイ、コンテキストメニュー、ドラッグ＆ドロップ、ショートカット。
4. **クロスプラットフォーム対応**:
   - Windows, macOS, Linux の 3 大 OS へのネイティブ対応。
   - 日本語を含む CJK IME 入力、ダークモード/ライトモード、OS ネイティブダイアログ。

## 3. GPUI の特徴と VHA との親和性

### 3.1 GPUI とは
- **Zed Industries** が開発するオープンソースの Rust 製 UI フレームワーク。
- GPU（Metal, DirectX 12 / Vulkan 等）による即時・保持ハイブリッド描画。
- Tailwind CSS ライクな宣言的レイアウト DSL（Flexbox ベース、Taffy エンジン採用）。
- モデル/ビューのアクター的リアクティブ状態管理（`Entity`, `Model`, `Context`）。

### 3.2 適合する点（親和性が高い領域）
| 項目 | 評価 | 解説 |
|---|---|---|
| **メモリ使用量・起動速度** | ◎ 絶大 | Chromium / WebView を完全に排除できるため、メモリ消費量が数百MBから数十MBへと劇的に削減され、瞬時起動が可能になる。 |
| **サムネイルの GPU 描画** | ◎ 最適 | GPU ダイレクトレンダリングにより、数千件のサムネイルのスクロール時における 120fps / 60fps 維持性能が非常に高い。 |
| **バックエンドとのゼロコスト統合** | ◎ 最適 | Rust コア（Tauri 移行で整備された `hub.rs`, `media.rs`, `face.rs`, `face_infer.rs`）と FFI/IPC を介さずメモリ上で直接ゼロコピー連携可能。IPC シリアライズのオーバーヘッドが皆無になる。 |
| **単一言語スタック (Pure Rust)** | ◯ 高 | フロント・バックエンドが全て Rust となり、言語境界やビルドチェーンの分断が解消する。 |

### 3.3 課題・ギャップ（現時点で困難な領域）
| 課題項目 | リスク度 | 詳細 |
|---|---|---|
| **動画プレビュー / 再生エンジン** | **極大 (Critical)** | GPUI には `<video>` タグのような組み込みメディアプレーヤーが存在しない。ホバープレビューや動画再生を行うには、FFmpeg / GStreamer / wgpu テクスチャ共有を自前で実装する必要がある。 |
| **プラットフォーム対応（特に Linux/Windows）** | **高 (High)** | GPUI は元々 macOS（Metal）向けに作られ、Windows / Linux サポートは Zed の進展に伴い急速に改善中だが、WebView2 / GTK ほど枯れておらず、ディスプレイスケーリングやグラフィックドライバ固有の不具合リスクがある。 |
| **CJK IME（日本語入力）の安定性** | **中〜高** | 検索バーやタグ入力、人物名入力において IME 変換ウィンドウの位置制御や未確定文字列のインライン描画など、Web 標準に比べ挙動の安定化に追加のケアが必要。 |
| **UI コンポーネントの再実装コスト** | **大 (High)** | Angular 側の UI コンポーネント（40以上のコンポーネント、40以上のパイプ、モーダル、スライダー、ドロップダウン、カラーピッカー等、約 23,000 行の TS/HTML/CSS）を全て GPUI のコンポーネントとしてゼロから書き直す必要がある。 |
| **多言語対応 (i18n)** | **中** | Angular では `@ngx-translate/core` で容易に実現されているが、Rust / GPUI 側で Fluent や `gettext` 等のローカライゼーション基盤を組む必要がある。 |

## 4. 移植パターンとアーキテクチャ比較

### パターン A: フル GPUI ネイティブ移植（Pure Rust）
- **構成**: 全 UI を GPUI で再構築、バックエンド（`src-tauri` のコア）を直接結合。
- **メリット**:
  - 最高峰の描画パフォーマンスと最小のフットプリント（メモリ数十MB）。
  - 完全な単一バイナリ配布が可能。
- **デメリット**:
  - 実装工数が膨大（推定 1.5 〜 2 人年規模）。
  - 動画再生・テクスチャ共有パイプラインの自前開発が必須。

### パターン B: Tauri 2 完遂（現行路線）
- **構成**: UI は既存の Angular を活用、バックエンドを Tauri 2 (Rust) で統一。
- **メリット**:
  - 既存の巨大な UI 資産（2万行超）を 100% 活用できる。
  - Web 標準のメディア機能（`<video>`, `<audio>`, Canvas）がそのまま動く。
  - すでに `integration/tauri-face-recognition` 等で大半のコアロジック（スキャン・ハブ保存・ONNX 推論）が実装済み。
- **デメリット**:
  - WebView のメモリフットプリント（約 150MB〜300MB）が残る。

### パターン C: ハイブリッド / 段階的 PoC（推奨ロードマップ）
- **構成**: コアロジック（`vha-core` クレート）の独立化を進めつつ、GPUI 上で「サムネイルギャラリー専任ビューア」としてのプロトタイプを開発・検証する。

## 5. コスト・工数見積もり（概算）

フル GPUI 移植を行った場合の主要コンポーネント別工数見積もり：

| フェーズ / 機能領域 | 工数規模 (人月) | 主な作業内容 |
|---|---|---|
| **Phase 1: コア分離 & 状態管理** | 1.0 〜 1.5 | `src-tauri` から UI 非依存のクレート抽出、GPUI Model/AppState 定義 |
| **Phase 2: 仮想スクロール & ギャラリー** | 1.5 〜 2.0 | GPUI `List` / `UniformList` による数万サムネイルの仮想グリッド、非同期画像ロード/テクスチャキャッシュ |
| **Phase 3: フィルタ・検索・ソート** | 1.0 〜 1.5 | 40以上のパイプ・フィルタロジック（あいまい検索、タグ、人物、解像度等）の Rust 実装 |
| **Phase 4: サイドバー・モーダル・設定 UI** | 1.5 〜 2.0 | 複雑な設定画面、リネーム、人物管理、タグ編集等の UI コンポーネント実装 |

| **合計** | **7.5 〜 11.0 人月** | |

## 6. 技術的ブレークダウンと検証ポイント

### 6.1 仮想スクロール（Virtual Scrolling）
- GPUI は `gpui::UniformList` や `gpui::List` を提供しており、行の高さが均一または計測可能なリストの仮想化は得意とする。
- ただし、VHA は「サムネイル表示」「詳細表示」「ファイル表示」「クリップ表示」など複数の動的レイアウト・可変幅グリッドを持つため、GPUI 上でリサイズ対応の Masonry / Virtual Grid を構築する設計が必要。

### 6.2 画像・サムネイルキャッシュ
- VHA は 1 画面に数十〜数百枚の JPEG サムネイルを表示し、高速スクロールする。
- GPUI では `image_cache` またはテクスチャアトラスを活用し、バックグラウンドスレッドでデコードした `image::RgbaImage` を GPU テクスチャにアップロードするパイプラインを組む必要がある。
- Rust ネイティブでの画像デコード（`image-rs`）は極めて高速であるため、WebView の `<img>` タグのメモリプレッシャーを回避できる利点がある。

### 6.3 動画クリッププレビューのハードル
- Electron / Tauri では `<video src="...">` を書くだけで Chromium / OS のハードウェアアクセラレーション付きデコーダが再生してくれる。
- GPUI では標準でビデオコンポーネントがないため、以下のいずれかが必要：
  1. **静止画連番方式**: ホバープレビュー（フィルムストリップ）のみに割り切り、動画再生は外部プレーヤー起動とする。
  2. **ffmpeg-next / gstreamer 連携**: 自前でフレームをデコードし、GPUI の `paint` パスでフレームテクスチャを毎フレーム転送する（実装難易度・CPU/GPU 負荷大）。

## 7. 結論と推奨アクションプラン

1. **現段階の判断**:
   - VHA 3 の現有資産（Angular の UI/UX 完成度、動画プレビュー機能）を考慮すると、**今すぐ GPUI に全面移行することは工数・リスクの観点から推奨されない**。
   - **Tauri 2 への移行**が、Web UI の資産を活かしつつバックエンドを Rust 化する最適解である。

2. **将来の GPUI 化に向けた具体的準備（Next Steps）**:
   - **ステップ 1: コアロジックのクレート分離 (`vha-core`)**
     - `src-tauri` の中の `hub.rs`, `media.rs`, `storage.rs`, `face.rs`, `face_infer.rs` を、Tauri に依存しない独立したクレート（`crates/vha-core`）として切り出す。
     - これにより、フロントエンドが Tauri であろうと GPUI であろうと同一のエンジンを共有できる。
   - **ステップ 2: 小規模な GPUI 実験（Spike / PoC）の実施**
     - `tools/gpui-spike` などのサブディレクトリで、`vha-core` を読み込んで「ハブ内のサムネイル一覧を GPUI で高速仮想スクロールする」だけの最小プロトタイプを作成し、描画パフォーマンス・メモリ・描画品質を実測する。
   - **ステップ 3: GPUI エコシステム（動画・ウィジェット・Windows/Linux）の定点観測**
     - GPUI 本体のリポジトリのリリース状況や、コミュニティによるメディア再生・ウィジェットライブラリの登場を待つ。
