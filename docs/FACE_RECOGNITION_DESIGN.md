## 1. 目的とスコープ

### 1.1 やること

1. **顔サムネイル**: 各動画から顔を検出し、顔の切り抜き画像（サムネイル）を生成・表示する
2. **人物分類**: 顔の特徴量で同一人物を自動的にグループ化する（名前なしの「人物」単位）
3. **人物フィルタ**: 人物を選ぶとその人が出ている動画に絞り込める。既存のタグフィルタと同じ操作感にする
4. **名前付け**: 人物に任意の名前を付けられる（分類の後付けラベル。推論には使わない）
5. **（任意）属性推定**: 年齢・性別の推定を人物単位の集約値として表示する（§5.8）。既定オフのオプトイン機能で、本体（1〜4）の動作には一切影響しない

### 1.2 やらないこと

- 属性推定のうち年齢・性別以外（表情、人種など。buffalo パックにモデルがなく、対象外）
- 本人確認・認証などセキュリティ用途
- クラウド送信。全処理はローカル完結
- 本家（whyboris/Video-Hub-App）への PR
- GPU 対応（v1 は CPU のみ。§13 の将来課題）

### 1.3 非機能要件

- 既存のサムネイル抽出を遅くしないこと。顔スキャンは独立したキューで、無効時は完全に無動作
- ライブラリ全件スキャンが現実的な時間に収まること（Phase 0 で実測し、§11 の基準で判定）
- スキャン結果は hub ごとに永続化し、再起動で再計算しないこと
- モデルを差し替えた場合に、古い特徴量と混ざらないこと（§6.4）

## 2. 現行コードの前提（実測した事実）

設計は以下の現行実装に乗せる。新規の仕組みは最小限にする。

| 項目 | 現行 |
|---|---|
| 構成 | Angular 20（renderer）+ Electron 42（内部 Node 24 / Chromium 148）、TypeScript |
| 動画メタ・画像抽出 | `node/main-extract.ts`: ffmpeg-static で ①単体サムネイル（再生時間の 1/10 地点）②フィルムストリップ（N 枚を横連結した 1 枚 JPG）③プレビュークリップ を生成する純関数群 |
| 抽出キュー | `node/main-extract-async.ts`: `async.queue`（並列度 1）で metadata / thumb / delete の 3 キュー。進捗は IPC で Angular へ通知。抽出中は `powerSaveBlocker` でスリープ抑止 |
| 出力先 | `<出力フォルダ>/vha-<hub名>/` 配下に `thumbnails/`、`filmstrips/`、`clips/`（ファイル名は動画の `hash`） |
| データ | `.vha2` ファイル = `FinalObject`（`interfaces/final-object.interface.ts`）。`images: ImageElement[]` が本体で、各要素に `hash`、`tags?: string[]` 等。人物用の項目はない。`screenshotSettings` は hub 単位で `FinalObject` 内に保存される |
| スクリーンショット既定値 | 高さ 288px、1 動画あたり 10 枚（`node/main-globals.ts` の `GLOBALS.screenshotSettings`、許容高さは 144〜504px） |
| フィルタ | `src/app/pipes/` に機能別 pipe が並ぶ方式（タグ、年、解像度など）。人物フィルタも pipe を 1 本足す形が既存パターンに合う |
| パッケージング | electron-builder。`electron-builder.json` の win/mac に `asarUnpack` 指定あり（現在は ffmpeg-static と ffprobe のみ）。**linux セクションには asar / asarUnpack の指定がない**（§9.3 で要確認） |
| テスト | 自動テストの仕組みはない。検証は `npm run check`（tsc + lint）と手動確認が現行水準 |

### 2.1 既存サムネイルを顔認識に流用しない理由

- 高さ 144〜504px に縮小済みで、画面端の顔は数十 px しかなく、検出・認識の精度が出ない
- フィルムストリップは複数フレームが横連結された 1 枚の JPG で、フレーム単位の時刻と座標が復元しにくい
- よって顔用フレームは別途、元解像度寄りで抽出する（§5.1）。既存資産は一切変更しない

## 3. 方式とモデル選定

### 3.1 方式

**onnxruntime-node + InsightFace の ONNX モデル**を Electron の utility process で動かす。

- 検出: SCRFD（顔の bbox + 5 点ランドマークを同時に出す）
- 認識: ArcFace 系（位置合わせ済み顔 → 512 次元埋め込み、L2 正規化）
- 同一人物判定: 埋め込み同士のコサイン類似度（正規化済みなので内積）

候補比較（face-api.js / Python サイドカー / クラウド API を却下した理由）は §12 に記録する。

### 3.2 モデルパックは 2 ファイルだけ使う（任意機能で +1）

InsightFace のパックには年齢性別・ランドマーク専用モデルも同梱されるが、分類に必要なのは検出と認識の 2 ファイルだけ。ランドマーク専用モデル（2d106 / 3d68）は取り込まない。属性推定（§5.8）を有効にする場合のみ `genderage.onnx` を追加で使う（両パックに同梱、数 MB 程度）。

| 構成 | 検出 | 認識 | 2 ファイルの合計 | 特徴 |
|---|---|---|---|---|
| **quality**（buffalo_l 抜粋） | `det_10g.onnx`（SCRFD-10GF） | `w600k_r50.onnx`（ResNet50@WebFace600K） | 約 180MB | 検出が強い。小さい顔・横顔・密集で差が出る |
| **light**（buffalo_sc） | `det_500m.onnx`（SCRFD-500MF） | `w600k_mbf.onnx`（MobileFaceNet@WebFace600K） | 約 16MB | パック全体でも 16MB と最小。高速だが検出の Hard 指標は 10GF に大きく劣る |
| **lvface**（D8 で追加） | `det_10g.onnx`（SCRFD-10GF、quality と同一） | `LVFace-T_Glint360K.onnx`（ViT-T@Glint360K、ByteDance） | 約 94MB | 認識が ArcFace の約 0.34 倍の時間で、精度は本用途の実測で互角（D8）。認識モデルは HuggingFace（bytedance-research/LVFace）から取得し、配布ファイル名のまま配置する |

参考値（公式の公表値）: 認識の LFW は buffalo_l 99.83 / buffalo_s 系 99.70 と差が小さい。一方、検出の WIDER FACE Hard は SCRFD-10GF 約 83 に対し SCRFD-500MF は約 68〜69 で、動画フレームで問題になるのは主にこちら。

- 埋め込みはどちらの認識モデルも 512 次元だが、**モデル間で空間が異なるため互換性はない**。切り替えたら再スキャンが必須（§6.4）
- 既定パックは Phase 0 の実測で決める（未決事項 D1）。推奨は quality（理由: 再スキャンのコストを考えると、最初から精度上限で走らせる方が手戻りが少ない。ただし §11 の時間基準を超える場合は light を既定にする）

### 3.3 ライセンス

- InsightFace のコードは MIT。ただし**学習済みモデルは非商用・研究目的のみ**で、商用利用には別途ライセンスが必要（InsightFace 公式の明記）
- LVFace（D8 の lvface パック）も同条件: コードは MIT だが**学習済みモデルの重みは非商用・研究目的のみ**（ByteDance）。個人用・無償の前提は変わらない
- 本 fork は個人用・無償という前提（冒頭）でのみモデルを利用する。前提が変わる場合はモデルを YuNet + SFace（Apache 2.0 / MIT 系、商用可）に差し替える。エンジン側の入出力契約（§5）はモデル非依存に保ち、差し替え可能にしておく
- モデルファイルはリポジトリにコミットしない。取得元 URL と SHA256 を付録 A に記録し、取得スクリプトで配置する（未決事項 D2）

### 3.4 実装上の本丸は ONNX 呼び出しではない

Python 版 InsightFace が内部でやっている以下を TypeScript に移植するのが主要な作業であり、Phase 0 の検証対象。

1. SCRFD の後処理: 3 ストライド（8/16/32）のアンカー生成、スコア / bbox / ランドマークのデコード、NMS
2. 顔の位置合わせ: 5 点ランドマークから ArcFace 基準テンプレート（付録 B）への相似変換を求め、112×112 にワープする
3. 画像処理: JPEG デコード、リサイズ、ワープ、切り抜き、JPEG 保存。現行リポジトリには画像処理ライブラリがないため **sharp（libvips の prebuilt バイナリ）を新規依存に追加**する

移植の正しさは「Python 版と同一画像で埋め込みのコサイン類似度が 0.999 以上」をもって確認する（§11 Phase 0）。

## 4. 全体アーキテクチャ

```
Angular (renderer)
  │  IPC: 'face-scan-request' / 'face-get-index' / 'face-rename-person' など
  ▼
Electron main (node/)
  ├─ main-extract-async.ts に faceQueue を追加（4 本目のキュー、並列度 1）
  ├─ main-face.ts          … キューから worker を起動し、結果を face-store に書く調停役
  └─ face-store.ts         … faces/index.json と embeddings.bin の読み書き（§6）
        │  MessagePort
        ▼
  utility process: face-worker
  ├─ face-frames           … ffmpeg で顔用フレーム抽出（main-extract の引数生成パターンを踏襲）
  ├─ scrfd.ts              … 検出（前処理・推論・後処理）
  ├─ arcface.ts            … 位置合わせ + 埋め込み
  ├─ image-ops.ts          … sharp のラッパ（デコード / リサイズ / ワープ / 切り抜き）
  └─ cluster.ts            … 動画内統合と全体クラスタリング（純関数、単体テスト可能に保つ）
```

### 4.1 utility process に分ける理由

- onnxruntime の推論は 1 フレームあたり数十〜数百 ms の CPU 処理で、main プロセスで回すと IPC やウィンドウ応答を詰まらせる恐れがある
- worker が落ちてもアプリ本体は落とさない（キュー側でその動画を `error` にして次へ進む。既存 `extractAll` の「失敗したら次のアイテムへ」の流儀に合わせる）
- モデルのロード（数百 MB 級の読み込み）は worker の起動時に 1 回だけ

### 4.2 依存の追加

| 依存 | 用途 | 備考 |
|---|---|---|
| `onnxruntime-node` | ONNX 推論 | プリビルトのネイティブバイナリ。プラットフォーム別に同梱されるため、配布サイズと asarUnpack が論点（§9） |
| `sharp` | 画像処理 | プリビルト（libvips）。同じく asarUnpack 対象 |

どちらも「Electron のバージョンに合わせたリビルド」は不要なプリビルト方式だが、Electron 42 環境での実動作は Phase 0 で要検証（§13）。

## 5. 処理パイプライン

対象は 1 動画 = `ImageElement` 1 件。顔スキャンの状態は動画ごとに `pending / done / none（顔なし）/ error` を持ち、再スキャン判定に使う。

### 5.1 フレームサンプリング

- 本数: `clamp(ceil(duration / 30秒), 10, 60)` 本を等間隔に取る。冒頭と末尾の各 2% は避ける（暗転・クレジット対策）
- 解像度: 元の縦横比のまま、幅の上限 1280px（それ以下は拡大しない）
- 抽出方法: 既存の `generateScreenshotStripArgs` と同様に `-ss` を入力側に付ける ffmpeg 方式。出力は一時フォルダ `faces/tmp/<hash>/` に個別 JPG（品質は既存に倣い `-q:v 2`）
- 一時フレームは処理後に削除する。残すのは顔の切り抜きだけ（§5.3）

### 5.2 検出（SCRFD）

- 入力: 640×640 にレターボックス（アスペクト維持 + パディング）、RGB、`(px - 127.5) / 128` で正規化、NCHW
- 出力デコード: ストライド 8/16/32、各セル 2 アンカー。スコア閾値 0.5、NMS の IoU 閾値 0.4（いずれも初期値、Phase 0 でサンプル実測して調整）
- 最小顔サイズ: 抽出フレーム上で短辺 40px 未満の検出は捨てる（遠景の群衆で顔サムネイルと分類がノイズ化するのを防ぐ。設定で変更可）
- 座標は元フレームに対する相対座標（0〜1）で保持し、解像度変更に強くする

### 5.3 顔サムネイルは 2 種類作る

| 種類 | 作り方 | 用途 | 保存 |
|---|---|---|---|
| aligned | 5 点ランドマークで位置合わせした 112×112 | 認識モデルの入力そのもの。人物の代表顔（アバター）表示 | **全ての検出顔**について保存 |
| display crop | bbox を 35% 拡張した正方形切り抜きを 256×256 にリサイズ | 動画詳細で見せる顔サムネイル（位置合わせ画像より自然で見栄えが良い） | **代表顔のみ**（§5.5 で選ばれた顔）保存 |

- 品質スコア = `det_score × sqrt(顔の面積比)` で代表顔を選ぶ（v1 は単純に。ブレ判定＝ラプラシアン分散は Phase 2 以降の改善候補として記録のみ）
- ファイル名は `<faceId>.jpg`。faceId は `<動画hash>-<連番>` とし、配置は §6.1

### 5.4 認識（ArcFace / LVFace）

- 入力: aligned 112×112 を NCHW 化し `(px - 127.5) / 127.5`
- 出力: 512 次元を L2 正規化して埋め込みとする。以後の類似度は内積のみ
- 認識の実装はパックごとに切り替える（`RecognizerKind`: quality / light は ArcFace、lvface は LVFace。D8）。LVFace の前処理は公式推論コードと等価であることをスパイクで確認済み（位置合わせテンプレートも同一のため aligned crop をそのまま使える）。入出力契約が同一でも埋め込み空間はモデルごとに異なるため、modelId で混在を防ぐ（§6.4）

### 5.5 動画内の統合

同じ動画の複数フレームに同じ人物が何度も映るため、そのまま全体分類に入れず動画内で先にまとめる。

- 動画内の埋め込み同士を貪欲にクラスタリング（閾値 `T_in`、初期値 0.50）
- グループごとに代表顔（品質スコア最大）を 1 つ決め、出現時刻のリスト（秒）を保持する
- 全体分類（§5.6）へ渡すのは代表の埋め込みと、その重みとして出現回数

### 5.6 全体クラスタリング（人物の生成）

- 方式: リーダーフォロワー法による逐次割当て。新規の（動画, 人物グループ）が来たら、各人物の重心（所属埋め込みの平均を再正規化）と比べて最大類似度が閾値 `T_global`（初期値 0.45）以上なら割当て、未満なら新規人物を作る
- 閾値は Phase 0 で 0.35〜0.60 のスイープを行い、同一人物の取りこぼし（分割）と別人混入（汚染）のバランスで決める（未決事項 D5）。**混入は後から直しにくいので、迷ったら分割側に倒す**（結合は手動操作で簡単、分割は面倒なため）
- 全件再クラスタリング（モデル変更時・閾値変更時用）も同じ `cluster.ts` の純関数として用意し、逐次割当てと結果が大きく乖離しないことをテストで担保する
- 人物 ID は `p000001` 形式の連番で永続化し、再クラスタリングでも可能な限り引き継ぐ（代表顔の faceId が一致する人物は同一 ID を維持）

### 5.7 失敗時の扱い

- フレームが壊れている / 動画が読めない: その動画を `error` として次へ（キューは止めない）
- 顔ゼロ: `none` として記録し、再スキャン対象から外す（設定変更時のみ再対象）
- モデル未配置 / ロード失敗: 機能全体を無効化して設定画面に理由を表示。アプリの他機能には影響させない

### 5.8 （任意）属性推定：年齢・性別

2026-10-23 に任意機能として追加が決まった。本体とは独立にオン/オフでき、オフのときはモデルも読まない。

- モデル: `genderage.onnx`（buffalo_l / buffalo_s の両パックに同梱）。位置合わせ済みの顔を入力し、性別（M/F）と年齢（整数の推定値）を返す。実装は §3.4 の移植対象に 1 モデル足すだけ
- **全顔には回さない**。コストとノイズの両面から、推論対象は（動画, 人物グループ）ごとに品質スコア上位の最大 5 顔に絞る
- **保存・表示は人物単位の集約値のみ**（§6.2）: 年齢はサンプルの中央値、性別は多数決とその一致率。フレーム単体の推定値はサンプルとしてだけ保持し、UI には出さない
- **実装上の確定事項（Phase 2、2026-10-23）**: ①顔ごとの推定値は index 等に一切永続化しない（§6.2 の任意 `attr` フィールドは実装しない。推定値は worker 内のサンプルとしてのみ存在する）②推論入力は「保存済みの aligned 画像」ではなく「該当フレームの再抽出＋bbox 切り抜き」の基準経路とする。aligned 画像を入力にする経路は実測で劣化した（Phase 0 の 63 顔で性別一致 55/63、年齢中央値誤差 7〜9 年）ため不採用。再抽出はサンプル顔のみなのでコストは小さい ③genderage.onnx は buffalo_l のみに同梱（§3 の記述は誤り）。light パック使用時は quality パック側のファイルを共用する
- 精度の前提（UI と設計の両方に効く）: 性別は正面の顔では比較的堅いが、年齢は平均で ±5〜7 歳程度の誤差が常態。よって表示は単一の数値ではなく**年代（20代、30代…）を本とし、数値は「推定」であることを明示**する。人物に手動で属性を付け直す項目は用意しない（推定値の上書きは名前付けで代替できる範囲）
- 集約の利点: 同一人物は多数のフレームと動画に現れるため、中央値と多数決で単体推論のブレがほぼ消える。これが静止画 1 枚の属性推定と本機能の決定的な差
- フィルタへの利用: 人物フィルタの補助条件（性別、年代）として Phase 3 以降で検討する。v1 の表示範囲は人物カードと人物一覧まで

## 6. データ設計

### 6.1 フォルダ構成（既存の出力先に相乗り）

```
<出力フォルダ>/vha-<hub名>/
  thumbnails/ filmstrips/ clips/     … 既存
  faces/
    index.json          … 顔・人物の索引（§6.2）
    embeddings.bin      … 埋め込みの実体（§6.3）
    aligned/<faceId>.jpg
    crops/<faceId>.jpg  … 代表顔の display crop のみ
    tmp/                … 作業用（処理後に空にする）
```

モデルファイルは hub ではなくアプリ側に置く（全 hub で共有）: `<userData>/face-models/<パック名>/` に `det_*.onnx` と `w600k_*.onnx`。

### 6.2 index.json スキーマ

```jsonc
{
  "version": 1,
  "modelId": "buffalo_l-r50",        // or "buffalo_sc-mbf"（§6.4）
  "clusterThreshold": 0.45,
  "videos": {
    "<動画hash>": {
      "status": "done",              // done | none | error
      "scannedAt": 1790000000000,
      "frameCount": 24,
      "faces": [
        {
          "faceId": "<hash>-0003",
          "t": 183.3,                // 出現時刻（秒）
          "bbox": [0.412, 0.203, 0.118, 0.211],  // x, y, w, h（相対座標）
          "score": 0.91,             // 検出スコア
          "quality": 0.83,
          "embeddingIdx": 17,        // embeddings.bin 内の位置
          "personId": "p000004",
          "representative": true,    // (動画, 人物) の代表か
          // 顔ごとの属性値（attr）は保存しない（Phase 2 確定、§5.8）。属性は PersonRecord.attributes の集約値のみ
        }
      ]
    }
  },
  "persons": [
    {
      "personId": "p000004",
      "name": "",                    // ユーザーが付けた名前（任意）
      "representativeFaceId": "<hash>-0003",
      "videoHashes": ["<hash>", "..."],
      "faceCount": 31,
      "hidden": false,
      "attributes": {                // 任意機能の集約値（§5.8）。無効時は項目自体がない
        "sex": "F",
        "sexAgreement": 0.93,        // 多数決の一致率
        "ageMedian": 28,
        "sampleCount": 42
      }
    }
  ]
}
```

### 6.3 embeddings.bin

- Float32 リトルエンディアン × 512 を連結しただけの単純形式。1 件 2048 バイト、`embeddingIdx × 2048` がオフセット
- 追記専用。再クラスタリングや削除で生じた空きは、再構築（コンパクション）で回収する
- 規模感: 1000 動画 × 平均 15 顔 = 15,000 件でも約 30MB。aligned 画像は約 4KB/枚で約 60MB。実用上問題にならない

### 6.4 モデルの同一性

- `index.json` の `modelId` が現在の設定と異なる場合、その hub の顔データは無効として扱い、再スキャンを促す。**異なるモデルの埋め込みを混ぜて比較してはならない**
- 人物の重心は保存せず、必要時に所属埋め込みから再計算する（モデル変更時の不整合を避ける）

### 6.5 .vha2 側の変更

- `ImageElement` に `persons?: string[]`（その動画に出ている人物 ID の一覧）を追加する。これは `faces/index.json` から導出できるキャッシュで、正は index 側
- hub を開くときに index と不整合があれば index から再生成する
- 任意項目の追加なので旧形式との互換は保たれるが、**旧バージョンのアプリで開いて保存すると `persons` が消える**可能性がある。fork 専用機能として許容する（§13 に記録）

## 7. 設定項目

hub 単位の設定として `FinalObject` に `screenshotSettings` と並べて `faceSettings` を追加する（人物データが hub 単位のため）。

| 項目 | 型 | 既定値 | 説明 |
|---|---|---|---|
| `enabled` | boolean | `false` | 顔スキャンの有効化（明示オプトイン） |
| `modelPack` | `'quality' \| 'light' \| 'lvface'` | D1 で決定 | §3.2 の 3 構成（lvface は D8 で追加） |
| `framesPerVideo` 上限 | number | 60 | §5.1 の本数計算の上限 |
| `sampleIntervalSec` | number | 30 | §5.1 の間隔 |
| `minFaceSizePx` | number | 40 | §5.2 の最小顔サイズ |
| `clusterThreshold` | number | 0.45 | §5.6 の `T_global`（上級設定として露出） |

グローバル側（`SettingsObject` / 設定ボタン）には、サイドバーに人物欄を表示するかのトグルだけを置く。

## 11. フェーズ計画と受け入れ基準

### Phase 0: スパイク（アプリに組み込まない）

場所は本リポジトリ外（ワークスペースの実験フォルダ）で、Node + onnxruntime-node の単体スクリプトとして作る。

作業:
1. モデル 2 ファイル × 2 構成を取得し、SHA256 を付録 A に記録
2. SCRFD 後処理 + 位置合わせ + ArcFace を TS で実装し、§10 の Python 版との一致を確認
3. サンプル動画（ユーザーの実ライブラリから数本、人物の正解が分かるもの）でフレーム抽出 → 顔サムネイル → クラスタリングまで通す
4. 計測: CPU での 1 フレームあたり処理時間（検出 / 認識別、構成別）、1 動画あたり総時間、1000 動画換算の推定
5. 閾値スイープ: `T_global` を 0.35〜0.60 で変え、分割数と混入数を記録（付録 C の表）

受け入れ基準:
- 埋め込みの一致（§10）が取れている
- サンプルでの人物分類が「目視で概ね正しい」と言える水準（混入は各人物 1 割未満を目安）
- 全件スキャン推定時間が quality 構成で 1000 動画あたり一晩（8 時間）を超えない。超える場合は light を既定にするか、サンプリング本数の見直しを D1 として再判断

### Phase 1: 検出 + 顔サムネイルの統合

- faceQueue、face-worker、face-store、設定（`enabled` / モデル配置）、進捗表示
- 動画詳細への顔ストリップ表示まで。**分類はまだ入れない**
- 受け入れ: §10 のキュー統合とパッケージング確認を通過。有効化 OFF のとき既存動作と差分ゼロ
- **完了（2026-10-23）**: 実装と検証の詳細は `tools/face-spike/PHASE1_RESULTS.md`。index スキーマには動画内グループの `groupId` / `representative` を §5.5 の統合結果として追加した（全体クラスタリングと personId は Phase 2 のまま）

### Phase 2: 分類 + 人物 UI

- cluster.ts の統合、サイドバー人物欄、人物フィルタ pipe、人物一覧ビュー、名前付け
- （任意）属性推定: genderage.ts の統合、人物単位の集約と人物カードへの表示（§5.8）。人物が確定しないと集約できないため、このフェーズに置く
- 受け入れ: サンプル hub で人物フィルタの結果が index の内容と一致。名前変更が再起動後も保持される。属性推定はオフ時に集約処理が走らないこと、有効時は既知のサンプル人物で性別が一致し年齢中央値が実年齢 ±7 歳以内に収まること
- **完了（2026-10-23）**: 実装と検証の詳細は `tools/face-spike/PHASE2_RESULTS.md`。全体クラスタリング閾値は D5 の T_global = 0.50 を使用。ID 安定化は代表埋め込みの類似度による貪欲な 1 対 1 対応付けで実装。検証中に Phase 1 の display crop が真っ黒になるバグ（float ジオメトリ）を発見・修正した。受け入れの「年齢中央値が実年齢 ±7 歳以内」は Phase 0 の実測（±10 歳級が常態）と矛盾するため、Phase 2 の検証では Phase 0 の集約値との差で評価した

### Phase 3: 手直し系と運用

- 人物の結合 UI、再クラスタリング、モデル切り替え時の再スキャン導線、統計表示
- 属性（性別・年代）による人物フィルタの補助条件はここで検討する
- 分割 UI（1 人物を 2 つに割る）は需要を見てから。データ構造は割れる形にしてある
- **完了（2026-10-24）**: 実装と検証の詳細は `tools/face-spike/PHASE3_RESULTS.md`。結合・分割・顔（グループ）の付け替え・代表顔の変更を人物一覧モーダルから操作できる。手動編集は index のピン（`manualGroups` / `manualUnassigned` / `manualRepFaces`）として保存され、再クラスタリングではピンを最優先で再構築するため、編集した人物の構成は次の編集まで固定される。分割 UI も需要待ちにせず本フェーズで実装した。属性（性別・年代）による人物フィルタの補助条件は検討のうえ見送り（人物フィルタは人物単位で完結しており、属性は推定誤差が大きく絞り込み条件にすると実在人物を取りこぼすため。属性表示は人物カード・一覧のまま）

各フェーズは独立にコミットを分け、フェーズ単位で動作確認してから次へ進む。

## 12. 代替案と却下理由（検討記録）

| 案 | 却下理由 |
|---|---|
| face-api.js / Human（renderer で TF.js） | 統合は最速だが精度と速度が中程度で、全件スキャンの本命には弱い。配布の手軽さは魅力なので、Phase 0 で Node 移植が頓挫した場合の退避先として残す |
| Python サイドカー（InsightFace を子プロセス） | 精度検証は最速だが、配布時に Python 一式の同梱が必要で本命にしない。ただし Phase 0 の「正解データ生成」には Python 版を使う |
| クラウド API（Rekognition 等） | ローカル動画のフレームを外部送信することになり、ローカル完結という本アプリの性格と合わない |
| OpenCV（YuNet + SFace） | ライセンスは最もクリーンだが、本 fork の前提（非商用でよい）では精度で勝る InsightFace を選ぶ理由が勝つ。商用化する場合の差し替え先として §3.3 に明記 |

## 13. リスクと対策

| リスク | 対策 |
|---|---|
| onnxruntime-node / sharp のプリビルトが Electron 42（Node 24）で動かない | Phase 0 でアプリ組み込み前に単体 + Electron 実機の両方で確認。動かない場合はバージョン固定か、推論を外部 Node プロセスに逃がす案に切り替える |
| 全件スキャンが想定より遅い | バックグラウンドキュー前提の設計にする（中断・再開可能、処理済みはスキップ）。サンプリング本数と最小顔サイズが主な調整ノブ |
| 人物の混入（別人と同一人物扱い） | 閾値は分割側に倒す方針（§5.6）。結合は手動で簡単、混入の除去は面倒なため |
| CPU 負荷と発熱・電力 | 既存抽出と同じく `powerSaveBlocker` の扱いに合わせ、キューは並列度 1。スレッド数の上限も設ける（§7） |
| 旧バージョンのアプリで hub を開くと `persons` が落ちる可能性 | fork 専用機能として許容。正データは `faces/index.json` 側にあり、開き直せば再生成できる（§6.5） |
| モデルの出自と再配布 | リポジトリにコミットしない。取得元と SHA256 を付録 A に残し、第三者が再現できる形にする |
| プライバシー | 全処理ローカル。ネットワークアクセスはモデル取得時のみ（それも手動手順を既定とする） |

将来課題: GPU 実行（Windows の DirectML、Mac の CoreML プロバイダ）、ブレ顔の品質判定、顔の出現時刻へのジャンプ再生、人物の分割 UI。

## 付録 C. Phase 0 計測の記録様式

閾値スイープ（実測、2026-10-23）: サンプルは YouTube の BBC 公式動画 6 本（Graham Norton Show のクリップ 4 本 + Attenborough のインタビュー等 2 本、同一人物が複数動画に登場する構成）。正解人物数はラベル付けできた実在の 11 人。詳細は `tools/face-spike/CLUSTER_RESULTS.md`。

| T_global | 人物数（推定 / 正解） | 分割した実人物 | 混入のある人物 | 備考 |
|---|---|---|---|---|
| 0.35 | 16 / 11 | 3（Gosling, Cleese, Attenborough） | 1（Norton が無関係ゲストのクラスタに吸収） | 重心ドリフトによる混入 |
| 0.40 | 16 / 11 | 3（同上） | 1（同上） | |
| 0.45 | 17 / 11 | 4（+ Unknown ゲスト B） | 1（Norton と Unknown ゲスト B の片方が混入） | 初期値はここだったが混入が残る |
| 0.50 | 18 / 11 | 4（Gosling, Cleese, Unknown ゲスト B, Attenborough） | 0 | **推奨（D5 決定値）** |
| 0.55 | 18 / 11 | 4（同上） | 0 | 0.50 と同一の割当て |
| 0.60 | 18 / 11 | 4（同上） | 0 | 0.50 と同一の割当て |

分割の内訳はすべて原因が説明できる: Gosling は俯き劣化顔、Cleese は手で顔を覆った遮蔽顔、Attenborough は約 60 歳の年齢差がある若年期アーカイブ映像（類似度が実質 0 で、モデル上は別人）。動画をまたぐ統合は Davies（類似度 0.837）、Gosling（0.752）、Attenborough 高齢期（0.635）の 3 組すべてが全閾値で成立した。
