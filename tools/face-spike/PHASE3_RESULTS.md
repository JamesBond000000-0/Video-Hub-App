## 実装内容（コミット単位）

1. **型と基盤**（`69353c9`）: `FaceIndexFile` に手動編集ピン 3 種を追加。`manualGroups`（グループキー `"<videoHash>#<groupId>"` → personId）、`manualUnassigned`（未割当てに固定するグループキー）、`manualRepFaces`（personId → 代表顔 faceId の手動指定）。グループキーの生成ヘルパー `faceGroupKey` もここ
2. **クラスタリングのピン対応＋編集操作**（`c2a5fc6`）: `clusterizeIndex` がピンを尊重するよう拡張し、編集のサージェリ関数（`mergePersonsInIndex` / `splitPersonInIndex` / `moveGroupsInIndex` / `setPersonRepresentativeInIndex`）を cluster.ts に追加。方式は次節
3. **FaceStore の編集 API**（`e125564`）: `mergePersons` / `splitPerson` / `moveGroups` / `setPersonRepresentative`。`applyClustering` が剪定済みピンを index に書き戻すよう拡張
4. **IPC**（`f1b0932`）: `face-merge-persons` / `face-split-person` / `face-move-groups` / `face-set-person-representative`。構成変更系は属性有効時に集約の再計算まで行い、常に応答として最新の payload（personsByVideo 込み）を返す
5. **Angular UI**（`b748343`）: 人物一覧モーダルの拡張（後述）と FaceService の編集送信・グループ取得（`groupsOfPerson`）、i18n（en.json のみ、PERSONS に 20 キー追加）
6. **ハーネス**（`54f6996`）: `tools/face-spike/phase3-harness.cjs`（検証結果は後述）

## 手動編集の保持方式（本フェーズの中心）

### ピンと「触れた人物の凍結」

- 編集はすべてピンとして表現する。結合は「関係する全グループ → 存続人物」のピン、分割は「移動グループ → 新人物」と「残りグループ → 元人物」のピン、付け替えは「対象グループ → 移動先」のピン＋関係人物の残りグループのピン、未割当ては `manualUnassigned` へのピン、代表顔は `manualRepFaces` への記録
- つまり**手動編集で触れた人物は、その時点で構成が凍結される**。凍結された人物は、その後何回再クラスタリングしても構成が変わらない（新しいスキャンで増えたグループが自動で入ることもない）。触れていない人物は従来どおりクラスタリングと ID 継承の対象
- 凍結を解く手段は次の手動編集だけ（結合で吸収する、グループを動かす等）。「全ピンを外して自動分類に戻す」操作は用意していない（必要なら将来課題）

### 再クラスタリングでの扱い（clusterizeIndex）

- ピン済みグループは自由クラスタリングの入力から外し、ピン先の人物の下にそのまま再構築する。人物の名前・非表示は ID の直接参照で引き継ぐ（類似度マッチングは使わない）
- ピン済み人物は ID 継承マッチングの対象からも外す。自由クラスタが偶然ピン済み人物の ID を奪うことはない
- 代表顔は `manualRepFaces` の指定が最優先（その顔が人物に属している間）。なければ従来どおり最高品質のグループ代表
- 属性集約は従来規則のまま: 人物のグループ集合が前回と完全一致する場合のみ引き継ぐ。凍結された人物は構成が不変なので集約は保持され、構成が変わる編集をした人物は集約が落ちて次回の属性計算で再計算される
- 存在しなくなったグループ（動画の再スキャン・削除）や人物を指すピンは、再クラスタリング時に剪定して index から落とす

### 編集の適用経路（サージェリ＋再クラスタリングで実体化）

- 編集関数（cluster.ts）はピンと人物レコードの生成・削除だけを操作し、顔 → 人物の割当ては触らない。FaceStore が編集のたびにピン対応の再クラスタリングを実行して実体化する。割当てを決めるコード経路が 1 本（clusterizeIndex）に保たれるため、「編集直後の状態」と「その後再クラスタリングした状態」が原理的に一致する
- 結合の存続規則: 引数の順で**最初に名前が付いている人物**が存続する（名前なし同士なら先頭）。存続人物が名前・非表示・代表顔の指定を引き継ぎ、消える人物の名前は失われる。消えた人物の ID は再利用しない（採番は `nextPersonSeq` の単調増加を維持し、FaceStore.splitPerson も既存最大値より上を採る）
- 分割は「全グループの移動」を拒否する（それは分割ではなく付け替え）。付け替えは全グループでも可で、元人物が空になればレコードは消える
- 付け替えの単位は顔 1 件ではなく **(動画, グループ)** に統一した。全体クラスタリングの割当て単位がグループであり、顔単位の移動は再クラスタリングで保持できない（グループ代表の埋め込みで判定するため、バラした顔は次回戻ってしまう）ため。グループ内の出来の悪い顔だけを外したい場合は、その動画のグループ自体を動かす運用になる

### 代表顔の変更の制約

- display crop（人物カードの画像）はグループ代表顔についてのみ保存されている（§5.3）。そのため UI で選べる代表顔は「その人物の各グループの代表顔」に限った。データ層（`setPersonRepresentativeInIndex`）は人物に属する任意の顔を受け付けるが、crop のない顔を指定するとカード画像が表示できないため、UI からは渡さない

### .vha2 キャッシュとの整合

- 編集系 IPC はすべて応答に最新の payload を載せるため、Phase 2 の既存経路（payload の personsByVideo → FaceService が ImageElement.persons を照合・書戻し → 通常の保存フロー）のままキャッシュが追随する。専用経路は作っていない。ハーネスでは導出元である personsByVideo と persons の整合を全編集後に確認した

## Angular UI（人物一覧モーダルの拡張）

- **結合**: ヘッダの「Merge people」で結合モードに入り、各カードのチェックボックスで 2 人以上を選んで結合ボタン。2 段階確認（1 回目のクリックでボタンが「Confirm merge」に変わり、2 回目で実行）
- **分割・付け替え**: 各カードの「Groups」でその人物のグループ一覧パネルを開く。各行はグループ代表の crop・動画ハッシュ・顔数・最初の出現時刻を表示し、行頭チェックで複数選択できる。移動先セレクトは「(new person)」「(unassigned)」「他の全人物」で、「(new person)」が分割、それ以外が付け替え。いずれも 2 段階確認。分割は全グループ選択時は実行不可（ヒント表示）
- **代表顔の変更**: グループ行の「Set as representative」でそのグループの代表顔を人物の代表顔に指定。現在の代表には「★ Representative」を表示
- **未割当ての戻し先**: 未割当てグループがある場合、一覧の下に「Unassigned face groups」節が出て、人物を選んで各グループを戻せる（可逆な操作なので確認なし）
- 確認はアプリのモーダル（modal.component）が情報表示専用でボタンを持たないため、UI 内の 2 段階確認で代替した

## 検証結果

ハーネス: `tools/face-spike/phase3-harness.cjs`（Phase 1/2 と同じ BBC 6 本を実スキャンし、FaceStore の編集 API を実走）。識別は Phase 0 ラベルのグループ転移による。なお Gosling 断片（p000013）の Phase 0 ラベルは tentative だったが、グループ照合の類似度は 0.928 と高く、Phase 2 の目視内訳でも Gosling 断片と確定しているため同定に使った（転移の合否はラベルの tentative でなく照合類似度 ≥ 0.45 で判定）。

### ビルド

- `npm run check:tsc`（renderer / main / worker の 3 プロジェクト）: 合格
- `npm run build`（Angular 本番ビルド）: 成功。警告は既存の 2 件のみ（file-path.service の `path` 依存、ng-qrcode の `qrcode` 依存。Phase 2 のベースラインと同一）

### ベースライン（Phase 2 状態の再現）

- 顔 72 件、人物 24、`nextPersonSeq` = 25（Phase 2 と完全一致 = 編集前の状態に回帰なし）

### 結合

- 名前を付けた主人物（p000011、4 顔）に断片（p000013、1 顔）を、**断片を先に渡して**結合 → 存続は名前付きの p000011。人物数 24 → 23、結合後の顔数 5（= 4 + 1）、名前「Ryan Gosling」を保持
- 結合した人物の属性集約は無効化され、無関係な Mack（p000002）の集約は保持された。personsByVideo から断片 ID が消えた

### 分割

- Davies（p000003、2 動画 2 グループ）から V9Dq のグループを分割 → 新人物は **p000025**（ベースラインの nextPersonSeq から採番。結合で消えた p000013 の再利用ではない）。人物数 23 → 24、Davies は yuXG のみ、新人物は V9Dq のみ、Davies の属性集約は無効化

### 付け替え

- 分割したグループを未割当てへ → 新人物は空になって消滅（人物数 24 → 23）、グループの顔は personId なしになり、personsByVideo からも落ちた
- 続けて Attenborough（p000001）へ付け替え → 顔が p000001 に移り、人物の videoHashes に V9Dq が加わり、属性集約は無効化。人物数は 23 のまま

### 代表顔の変更

- Norton（p000007、4 グループ）の代表顔を別グループの代表顔（`yuXGpUR7fXA-0002`）へ変更でき、再読込後も維持。他人の顔への変更はデータ層で拒否された

### 再クラスタリングでの保持（合格条件の中心）

- 上記の全編集後に再クラスタリングを実行し、**人物数（23）・人物 ID 集合・全 72 顔の顔 → 人物割当てが編集直後と完全一致**。結合した Gosling の ID と名前、付け替えたグループの所属（Davies に戻らない）、代表顔の手動指定がすべて保持され、消えた ID（p000013、p000025）は復活しなかった
- ピンの保存も確認: 付け替えたグループは `manualGroups` で p000001 に、代表顔は `manualRepFaces` に記録されていた
- 2 回目の再クラスタリングでも割当て・人物数は不変（冪等）
- 無関係な Mack の属性集約は全編集＋再クラスタリングを通じて保持され、編集した 3 人物（結合・分割元・付け替え先）に古い集約は残らなかった

### 属性の再計算

- 結合後の Gosling について属性を再計算すると、新しい構成（主＋断片のサンプル）に基づく集約が付き、性別は M で一致（サンプル 5 件）。index.json に顔ごとの属性値が残らないことも再確認した
